# Fundación técnica del Agente de IA — arquitectura implementada

Esta es la base ejecutable del Agente de IA para la clínica dental: un monolito modular con arquitectura hexagonal (Python + FastAPI + LangGraph + PostgreSQL + Redis + YCloud + Dentalink). El diseño completo de producto, alcance del MVP y reglas de negocio viven en [`PRD.md`](../PRD.md) — este documento cubre únicamente lo que ya está construido en el código, tal como existe hoy.

## Quick path

1. `cp dotenv_example_template.txt .env` y completá tus datos reales de Postgres/Redis (host, puerto, usuario, password, db) y, si vas a probar contra integraciones reales, las credenciales de YCloud, Dentalink y del LLM (ver `Settings` en `app/config/settings.py` para el listado completo — cualquier integración sin credenciales cae automáticamente a su adaptador Fake, ver tabla de abajo).
2. `docker-compose up -d postgres redis` (o apuntá `.env` a tu propio servidor).
3. `uv sync --frozen --extra dev` (el proyecto usa `uv`, no `pip install -e`; hay `uv.lock` versionado y así es como corre en CI).
4. `uv run python -m alembic upgrade head` (10 migraciones, `0001` a `0010`).
5. `uv run pytest` → 1082 tests. Verde salvo lo que necesite Postgres/Redis reales corriendo (todo `tests/integration/`, incluido `test_checkpointer_postgres.py`) si no los tenés levantados localmente.
6. `uv run python -m app.main` (o `uv run uvicorn app.main:app`) → `GET /health` y `GET /ready` deberían responder 200 (`/ready` verifica Postgres y Redis).

## Details

| Tema | Decisión |
|------|----------|
| Carpetas | Árbol hexagonal: `domain/application/infrastructure/api/agent/config/workers`, no la plantilla genérica en capas de `fastapi-templates`. `app/agent/nodes/` concentra los nodos del grafo; `app/application/` está dividido por sub-dominio (`appointments`, `agreements`, `admin`, `audio`, `config`, `conversations`, `errors`, `handoff`, `memory`, `messages`, `observability`, `patients`, `pending_actions`, `specialties`). |
| Dominio | ~25 entidades (`app/domain/entities/`) y ~24 Protocols de repositorio/gateway (`app/domain/repositories/`), entre ellos `AppointmentGateway`, `PatientGateway`, `AgreementGateway`, `SpecialtyGateway`, `TreatmentGateway`, `MessagingGateway`, `HumanHandoffGateway`, `MediaGateway`, `MediaDownloader`, `TranscriptionGateway`, `LLMProvider`, `AgentInvoker`, `ConversationRepository`, `ContactRepository`, `ContactMemoryRepository`, `MessageRepository`, `AgentRunRepository`, `NodeExecutionRepository`, `ToolExecutionRepository`, `ErrorRepository`, `IncidentRepository`/`IncidentGateway`, `AlertNotifier`, `RuntimeConfigRepository`, `PendingActionRepository`, `ScheduledActionRepository`, `AdminUserRepository`/`AdminAuditLogRepository`, `KnowledgeRepository`. El dominio no importa FastAPI, SQLAlchemy, Redis ni LangGraph. `KnowledgeRepository`/`ApprovedContent` tienen tabla y repositorio SQLAlchemy pero ningún caso de uso ni nodo los consume todavía — es schema heredado del MVP inicial, sin lógica encima. |
| Grafo LangGraph | Grafo completo (PRD.md §29): `START → check_conversation_mode → resolve_interaction →` (`appointment` \| `agreement` \| `specialties` \| `handoff` \| `fallback`) `→ END`, con `handle_error` como sumidero de cualquier excepción. `check_conversation_mode` es un defense-in-depth re-check de `conversation.mode` (`IngestMessageUseCase` ya filtra modo `HUMAN` antes de invocar el grafo). `resolve_interaction` resuelve intención por botón determinístico (PRD.md §6) o clasificación LLM en texto/audio libre, con un escape hatch a `handoff` incluso a mitad de flujo. Cada nodo de negocio está envuelto por `with_error_handling` (`app/agent/nodes/error_handling.py`), que registra un `NodeExecution` (RUNNING→COMPLETED/FAILED) y abre un `TraceContext` para que cualquier gateway llamado dentro registre su propio `ToolExecution`, y ante una excepción no manejada crea un `ErrorRecord` (`source=langgraph`) y enruta a `handle_error`. `AgentState` (`app/agent/state.py`) incluye `recent_messages`/`contact_memory_summary` (memoria conversacional) además de los campos de PRD.md §31. `search_availability.py` es un nodo standalone de demo, ya no está wireado en `build_graph`. |
| Gestión de turnos | `appointment` es una máquina de estados de un solo nodo (`app/agent/nodes/appointment.py`) que cubre crear, reagendar y cancelar turnos (PRD.md §9-16, §32, §72) con 5 stages (`awaiting_operation_selection` → `awaiting_identification` → `awaiting_appointment_selection`/`awaiting_slot_selection` → `awaiting_confirmation`), identificación de paciente por nombre+DNI con alta de paciente nuevo si Dentalink no lo encuentra, `PendingAction` + `ScheduledAction` para el patrón propuesta→confirmación con revalidación de disponibilidad (`RevalidateAndCreateAppointmentUseCase`/`RevalidateAndRescheduleAppointmentUseCase`) justo antes de escribir en Dentalink, e idempotencia por `conversation_id`+`pending_action_id`. |
| Mensajería (YCloud) | YCloud es el único canal de WhatsApp (PRD.md §24). `YCloudMessagingGateway`/`YCloudHandoffGateway` (reales, `httpx`) están wireados en DI (`app/api/dependencies/gateways.py`) y se activan automáticamente cuando `YCLOUD_API_KEY` está configurada; sin esa credencial, caen a `FakeYCloudMessagingGateway`/`FakeYCloudHandoffGateway`. Cubre envío de texto, botones interactivos, indicador de "escribiendo…" (`send_typing_indicator`, disparado por `IngestMessageUseCase` antes de invocar al agente) y lectura de teléfono por `ycloud_contact_id`. El toggle bot/humano es bidireccional: `handoff` node pasa la conversación a `mode="human"`; el tag "Human" agregado/quitado en el Shared Team Inbox de YCloud dispara el webhook `contact.attributes_changed`, que `SyncConversationModeFromTagUseCase` traduce de vuelta a `mode="agent"`/`"human"` (y su `input_state` correspondiente). `YCloudMediaGateway` (descarga de adjuntos) existe implementada pero no está wireada — `get_media_gateway()` siempre devuelve el Fake. |
| Integración Dentalink | `DentalinkClient` (`httpx`) más 5 gateways reales — `DentalinkAppointmentGateway` (buscar disponibilidad, listar profesionales, turnos de un paciente, crear/reagendar/cancelar), `DentalinkAgreementGateway` (convenios, buscar por nombre, convenios de un paciente), `DentalinkPatientGateway` (buscar/crear paciente), `DentalinkSpecialtyGateway` (especialidades) y `DentalinkTreatmentGateway` (tratamientos de un paciente) — se activan en DI cuando `DENTALINK_ACCESS_TOKEN` está configurado; sin token, cada uno cae a su Fake homónimo. `TreatmentGateway` está wireado pero ningún nodo/caso de uso del grafo lo consume todavía — infraestructura lista, sin flujo conversacional encima. |
| LLM Provider | `OpenAICompatibleLLMProvider` (`httpx`, compatible con un endpoint tipo 9Router) se activa cuando `LLM_API_URL` está configurado; sin URL, cae a `FakeLLMProvider`. Implementa `classify_intent`/`extract_information`/`generate_response`/`summarize`, todos trazados vía `traced_call` (`ToolExecution`) y con errores tipados (`LLMAuthError`/`LLMTimeoutError`/`LLMInvalidResponseError` → `errors.error_type`). Modelo, temperatura y los 3 prompts (clasificación, extracción, generación) se leen en cada llamada desde `RuntimeConfigService`, no desde `Settings` — ver fila siguiente. |
| Configuración runtime (admin-editable) | `RuntimeAgentConfig` (una única fila, `id="default"`) vive en Postgres (`runtime_agent_config`, migración `0009`) con cache Redis de 10s delante (`RuntimeConfigService`, cache-aside, cualquier falla de Redis degrada a lectura directa de Postgres). Cubre `model`, `temperature`, `debounce_seconds` (el debounce real de `IngestMessageUseCase._debounce_and_process` se lee de acá en cada ventana, no de `Settings`) y los 3 prompts del LLM provider. `Settings.message_debounce_seconds` sigue existiendo solo como semilla del default (`_default_runtime_agent_config`) y como ventana propia, independiente, de `DebounceTracker` (detecta si un mensaje más nuevo "retocó" la ventana). **No hay todavía una ruta `/admin` para escribir esta config** (`GET /admin/config` solo expone booleans de "¿está configurada esta integración?", PRD.md §75.3) — cambiar model/temperature/prompts hoy requiere escribir la fila directamente en Postgres. |
| Memoria conversacional | 4 capas, sin número de sección propio en el PRD (brief de esta sesión): (1) historial persistente completo en `messages` (Postgres, nunca se borra salvo `ResetConversationUseCase`); (2) ventana reciente configurable (`memory_recent_window_size`, default 15) vía `MessageRepository.get_recent_by_conversation_id`; (3) resumen compactado por contacto (`ContactMemory`, una fila por contacto, actualizado incrementalmente por `MemoryService.compact()` con cache Redis de 1h) que solo guarda información útil a futuro, no transcripción; (4) estado operacional del turno en curso (`collected_data`/`pending_action_id` del checkpoint de LangGraph + `PendingAction`/`ScheduledAction` en Postgres). `MemoryService.build_agent_context()` arma `(recent_messages, contact_memory_summary)` y `LangGraphAgentInvoker.handle()` los inyecta en `AgentState` antes de cada `graph.ainvoke()`; ambos alimentan a su vez el prompt de `classify_intent`. La compactación (`app.workers.memory_tasks.compact_stale_contact_memories`) es una función pura, testeada, sin scheduler que la dispare periódicamente todavía. `POST /admin/conversations/{id}/reset` (solo rol `ADMIN_TECHNICAL` + CSRF) borra mensajes, memoria compactada, thread del checkpointer y vuelve `mode`/`input_state` a default — herramienta de testing, nunca para usar contra una conversación real. |
| Checkpointer | `AsyncPostgresSaver` con su propio pool `psycopg` (`autocommit=True` — `setup()` corre `CREATE INDEX CONCURRENTLY`, que Postgres no permite dentro de una transacción), abierto de forma perezosa en el primer `handle()` que lo necesita (`app/api/dependencies/checkpointer.py`) y cerrado en el lifespan de FastAPI. Pool separado del engine `asyncpg` de SQLAlchemy porque `langgraph-checkpoint-postgres` solo soporta `psycopg`(3). `Settings.checkpointer_database_url` expone el DSN en formato `postgresql://` plano (no `postgresql+asyncpg://`) porque `psycopg` no entiende el sufijo de dialecto de SQLAlchemy. |
| Pipeline de mensajes entrantes | Webhook YCloud (`POST /webhooks/ycloud/{secret}`, secreto comparado con `hmac.compare_digest`) → fan-out por `payload["type"]` (mensaje entrante vs. `contact.attributes_changed` para el toggle de tag) → dedupe por `external_message_id` → resolver/crear contacto y conversación (`ConversationId` = `ycloud-{telefono}`) → mensaje de bienvenida con menú de botones en el primer turno de una conversación nueva (enviado sync, no fire-and-forget) → si es audio: `MediaProcessingJob` + rate limit por conversación/minuto, sin tocar debounce/lock todavía → persistir mensaje → gate de modo `HUMAN` (corta antes de debounce) → debounce (duración leída en vivo de `RuntimeConfigService`, agrupa mensajes por conversación) → typing indicator best-effort → lock Redis por conversación → seam hacia `AgentInvoker.handle()`. Diseño de un solo worker Uvicorn: el acumulador de debounce vive en memoria de proceso (`IngestMessageUseCase` es singleton), no sobrevive un restart ni múltiples workers. |
| Observabilidad | Tablas `agent_runs`/`node_executions`/`tool_executions`/`errors`/`incidents` (migraciones `0005` y `0008`) con sus repositorios SQLAlchemy y entidades de dominio. Cada `LangGraphAgentInvoker.handle()` crea un `AgentRun` (running→completed/failed/handoff); cada nodo escribe su `NodeExecution`; cada llamada trazada (`traced_call`, usada por LLM/Dentalink/YCloud) escribe un `ToolExecution` colgado del `node_execution_id` activo vía `TraceContext` (contextvars, sin pasar el contexto explícitamente por cada capa). `ErrorService` clasifica severidad (PRD.md §46), agrupa por `(source, error_type)` dentro de una ventana para escalar WARNING→ERROR, y por encima de un segundo umbral abre/actualiza un `Incident` y notifica. `TelegramAlertNotifier`/`LinearIncidentGateway` (reales, `httpx`) están implementados pero **no wireados en DI** — `get_telegram_notifier()`/`get_linear_gateway()` siempre devuelven sus Fakes, sin credenciales de Telegram/Linear configuradas en este entorno. El sweep de recuperación de incidentes (`app.workers.incident_tasks.check_incident_recovery`) es una función pura testeada, sin scheduler. |
| Panel administrativo | `/admin/login`/`/admin/logout` (cookies `admin_session` HttpOnly + `admin_csrf`, sesión firmada, roles `ADMIN_TECHNICAL`/`ADMIN_CLINIC`/`READ_ONLY`, PRD.md §74.3), auditoría de accesos (`admin_audit_log`). Rutas de lectura para cualquier rol autenticado: `GET /admin/conversations`, `GET /admin/conversations/{id}` (mensajes + agent runs + errores), `GET /admin/errors`, `GET /admin/errors/{id}`, `GET /admin/runs/{agent_run_id}` (node + tool executions). Mutaciones solo `ADMIN_TECHNICAL` + CSRF: `POST /admin/errors/{id}/resolve`, `POST /admin/conversations/{id}/reset`. `GET /admin/config` expone únicamente booleans (¿Groq/YCloud/Dentalink configurados?, `internal_eval_enabled`) — no hay ruta para editar `RuntimeAgentConfig` (ver fila de configuración runtime). Los `/docs`/`/redoc`/`/openapi.json` públicos de FastAPI están deshabilitados (`app/main.py`); `admin_docs.py` los reexpone bajo `/admin/docs`/`/admin/redoc`/`/admin/openapi.json`, gateados por sesión admin. |
| Audio/transcripción | Schema completo en `messages` (migración `0006`: `media_id`/`media_mime_type`/`media_sha256`/`media_status`, `transcription`/`transcription_status`/`transcription_provider`/`transcription_model`/`transcription_error`) más tabla/entidad `media_processing_jobs`. `IngestMessageUseCase` ya persiste el mensaje de audio y crea el `MediaProcessingJob` con rate limit por conversación; `TranscribeAudioUseCase` (`app/application/audio/transcribe_audio.py`) hace el pipeline completo (descarga → transcribe → guarda texto → borra temporal → reingresa por `resume_after_transcription`). Los adaptadores reales están implementados pero **no wireados**: `GroqTranscriptionGateway` (Groq Whisper) y `SecureMediaDownloader` (descarga con protección SSRF) existen en `app/infrastructure/` pero `get_transcription_gateway()`/`get_media_downloader()` siempre devuelven sus Fakes — sin credenciales de Groq en este entorno. `app.workers.audio_tasks.process_pending_audio_jobs` (el poll de `MediaProcessingJob`s pendientes) es una función pura testeada, sin scheduler. |
| Evaluación (Promptfoo) | `POST /internal/eval/chat` (gateado por `INTERNAL_EVAL_ENABLED=true` + sesión admin, PRD.md §61) corre el grafo real contra el stack Fake completo y devuelve `node_names`/`tool_names` para que las assertions de Promptfoo verifiquen orden/presencia de pasos. `evals/promptfooconfig.yaml` + datasets (`appointments`, `agreements`, `handoff`, `audio`, `safety`, `adversarial`) apuntan a ese endpoint — el config está estructuralmente completo, pero correr `npx promptfoo eval` de verdad contra un servidor levantado no se hizo en este entorno (Node/promptfoo no forma parte del toolchain Python). |
| Migraciones | Alembic async, 10 revisiones: `0001_base` (no-op, prueba el pipeline) · `0002_core_schema` (patients, contacts, conversations, messages, appointments, appointment_actions, pending_actions, tool_executions, human_handoffs, approved_contents, outbox_events) · `0003_scheduled_and_media_jobs` (scheduled_actions, media_processing_jobs) · `0004_conversation_input_state` (columna `input_state`) · `0005_observability` (agent_runs, node_executions, tool_executions v2, errors — reemplaza el `tool_executions` de `0002`) · `0006_audio_transcription` (columnas de audio/transcripción en `messages`) · `0007_admin_panel` (admin_users, admin_audit_log) · `0008_incidents` (incidents) · `0009_runtime_agent_config` (runtime_agent_config) · `0010_conversational_memory` (columna `role` en `messages`, tabla `contact_memories`). |
| Testing y calidad | `uv` + `uv.lock` (no `pip install -e`), CI (`.github/workflows/ci.yml`) corre `uv sync --frozen --extra dev` → `ruff check .` → `mypy app/` (strict) → `pytest`. 1082 tests (`uv run pytest`), organizados en `tests/unit/` (mayoría, sin dependencias externas), `tests/integration/` (repositorios SQLAlchemy, migraciones, Redis, requieren Postgres/Redis reales) y `tests/agent/` (grafo, checkpointer). |

## Deploy

CI/CD vive en `.github/workflows/release.yml`, disparado al publicar un release de GitHub con tag SemVer exacto (`vX.Y.Z`): valida el tag → corre lint/type-check/tests → build-and-push de la imagen a `ghcr.io/fer336/agente-ai:<tag>` → un job (`pin-compose`) reescribe automáticamente la línea `image:` de `docker-stack.yml` en `main` y commitea el pin → `notify-portainer` dispara el webhook de redeploy del stack de Portainer/Swarm → `verify-health` sondea `https://agent.qeva-ai.com/ready` hasta 18 intentos (10s de intervalo) y falla el deploy si no vuelve healthy. `docker-stack.yml` es el artefacto de producción (Swarm, un solo réplica, secret `agente_ai_backend_env` montado como `/run/secrets/backend.env`, detrás de Traefik) — `docker-compose.yml` es exclusivamente para desarrollo local y la pipeline nunca lo toca. `entrypoint.sh` corre `alembic upgrade head` antes de levantar Uvicorn en cada arranque del contenedor.

Construir el/los proceso(s) worker/scheduler que hoy faltan por completo: disparar periódicamente `process_pending_audio_jobs`, `check_incident_recovery`, `compact_stale_contact_memories` y el vencimiento de `PendingAction`/`ScheduledAction` (PRD.md §16.1/§16.3) — las cuatro son funciones puras ya testeadas, ninguna tiene un loop/cron que las llame.
